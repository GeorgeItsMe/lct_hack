# Контур · Москоллектор

Сервис поддержки диспетчера для задачи №8 ЛЦТ. По журналу событий СМВУ он прогнозирует на 24 часа неисправности датчиков, пожарные и охранные сигналы по каждому объекту, объясняет прогноз, предлагает действие и сохраняет решение человека. Не больше одного предупреждения на объект и тип в сутки. Модель не управляет оборудованием.

На полигоне — реальном журнале с инцидентами, правда о которых известна, — сервис отличает возгорание от сварки и проникновение от работы по наряду, заранее предупреждает об отказах насосов и вентиляторов и о росте газа ([docs/POLYGON.md](docs/POLYGON.md)).

## Демо-стенд

https://contour.foundersmedia.online — Docker Compose (FastAPI + PostgreSQL 16) за nginx. Запасные адреса того же стенда: https://contour-lct.81.26.178.170.nip.io и https://contour-lct.81.26.178.170.sslip.io. Учётные записи ниже, пароль `contour-demo`. Если корпоративный фильтр блокирует адрес, откройте его из другой сети.

## Быстрый запуск

Нужны Python 3.12 и Node.js 24. Модели и срез архива 2026 года лежат в репозитории (`vercel_runtime/`), отдельно ничего скачивать не нужно.

```bash
git clone https://github.com/GeorgeItsMe/lct_hack.git && cd lct_hack
./scripts/run_local.sh
```

Скрипт установит зависимости, соберёт интерфейс и запустит сервис на http://127.0.0.1:8000. Интернет нужен только для первичной установки.

Docker с PostgreSQL:

```bash
cp .env.example .env
CONTOUR_PORT=8001 docker compose up --build -d
```

Вход: учётные записи `dispatcher`, `technician`, `analyst`, `manager`, `admin`, пароль `contour-demo` (демонстрационный режим; в промышленной среде отключается, см. [DEPLOYMENT.md](docs/DEPLOYMENT.md)).

## Проверка на своих данных

1. Войти как «Аналитик» → «Данные и загрузка».
2. Выбрать журнал СМВУ в формате выгрузки (CSV, XLSX, JSON, XML или ZIP), момент прогноза не указывать.
3. «Загрузить и рассчитать». Через несколько секунд появятся прогнозы по всем объектам, факторы и исходные сообщения.
4. Выйти из системы и войти как «Диспетчер». Расчёт сохранён на сервере и стоит в очереди проверки с пометкой «Загрузка аналитика · момент прогноза»; карточка открывается с факторами и исходными сообщениями, по ней можно принять решение. Техперсонал, руководитель и администратор видят те же данные в своих разделах.

Загружать данные может только аналитик: у остальных ролей раздела нет, API отвечает 403. В очередь диспетчера попадает последний завершённый расчёт по новым данным — загрузка аналитика или поток СМВУ.

Пример: [`examples/smvu_journal_2026-06-15.csv`](examples/). Для полного прогноза нужна неделя данных до момента прогноза; при меньшем объёме (от суток) прогноз выдаётся с пометкой неполной предыстории.

## Роли

| Роль | Рабочее место |
|---|---|
| Диспетчер | Очередь предупреждений (архив и поток СМВУ), схема объектов, карточка прогноза с долей подтвердившихся предупреждений, решение и журнал обработки, уведомления |
| Технический персонал | Состояние оборудования, задачи по решениям диспетчера, заявки во внешнюю систему и их статусы |
| Аналитик | Загрузка данных, верификация меток «прогноз → итог», наборы меток, предложение порогов, качество модели, полигон |
| Руководитель подразделения | Сводка по узлам, нагрузка на диспетчера, динамика и отработка, утверждение порогов, отчёты PDF/XLSX, полигон, критические уведомления |
| Администратор | Пользователи, роли и зоны ответственности, журнал аудита |

Основание в ТЗ, матрица прав и допущения: [docs/ROLES.md](docs/ROLES.md). Уровни риска (критический, высокий, повышенный, низкий) считаются относительно порога предупреждения и показаны в очереди, на схеме и в карточке.

## Сценарий показа

1. **Диспетчер.** Очередь на 15 июня 2026, 12:00 МСК. Открыть объект: срок действия предупреждения, сколько таких предупреждений подтвердилось в мае, факторы, рекомендации с основанием из журнала, проверка ситуации, календарный контекст. Вкладка «Решение»: действие и основание; через три часа предупреждение остаётся с этим решением. Реестры нарядов, огневых работ и видеонаблюдения заказчик не передал — в карточке так и написано: «реестр не передан». Ниже на той же странице — «Полигон · мир 101»: тревоги и предупреждения с известной правдой и метками «Огневые работы по наряду НД-…», «Доступ без наряда»; в их карточке «Проверка ситуации» показывает наряды, огневые работы и ремонты объекта.
2. **Технический персонал.** «Задачи и заявки»: черновик по решению диспетчера → передать в систему заявок; статус и итог приходят из эмулятора внешней системы. «Состояние оборудования»: неисправные каналы, прогноз отказа и «Насосы и вентиляторы» — последнее состояние каждого агрегата по журналу (включён, выключен, неисправен, молчит неделю) и прогноз отказа по износу на полигоне с паспортами агрегатов.
3. **Аналитик.** «Верификация данных»: принять метку, сохранить набор меток. «Пороги»: эффект нового порога на периоде настройки → предложение руководителю. «Данные и загрузка»: загрузить пример.
4. **Руководитель.** «Сводка и отчёты»: блок «За смену» (предупреждения, верные, ложные, пойманные заранее неспокойные сутки; итог известен через сутки, поэтому берётся последняя смена с известным итогом), нагрузка на диспетчера до и после правила 24 часа, утвердить порог, выгрузить PDF или XLSX. «Полигон»: что система распознаёт на инцидентах с известной правдой, лента июня, синтетический датасет.
5. **Администратор.** Пользователи и журнал аудита со всеми шагами.

Поток мониторинга: `python scripts/emulate_smvu.py --as-of 2026-06-15T12:05` отправляет реальные архивные события в API приёма; предупреждения по ним появляются в очереди диспетчера с пометкой «Поток СМВУ». Весь сценарий ролей проверяет `python scripts/verify_roles.py --url http://127.0.0.1:8000`.

## Качество

Правило предупреждений: **не больше одного предупреждения на объект и тип риска в сутки**. Прогноз отвечает, начнётся ли на объекте эпизод этого типа в ближайшие 24 часа, поэтому одно предупреждение уже покрывает сутки; повтор по тому же объекту и типу возможен не раньше чем через 24 часа. Правило одинаково для архивной очереди, потока СМВУ, загрузок аналитика, подбора порога и всех метрик.

Пакет `op-ead0f8f0b079`, расчёт каждый час. Модель для каждого типа и её порог выбраны на 15–31 мая: наибольшая полнота при точности не ниже 0,7, если она достижима, иначе лучший F1; июнь открыт один раз для выбранной модели. Точность и полнота считаются в одной единице — **неспокойные сутки**: эпизоды одного объекта и типа в пределах суток от первого — один случай. Случай пойман, если предупреждение выдано не раньше чем за 24 часа до его первого эпизода; предупреждение верно, если в следующие 24 часа начались новые неспокойные сутки. Продолжение уже идущих суток предупреждение верным не делает: оно ничего нового не предсказывает.

| Июнь 2026, каждый час | Модель | Precision | Recall (неспокойные сутки) | Предупреждений в сутки | Из них ложных | Медианное упреждение |
|---|---|---:|---:|---:|---:|---:|
| Охранный сигнал | смесь: 0,75 число эпизодов + 0,25 классификатор | **57,8%** | **40,2%** | 7,9 | 3,3 | 18,7 ч |
| Пожарный сигнал | классификатор | **25,9%** | **48,9%** | 4,0 | 3,0 | 17,1 ч |
| Неисправность ≥1 часа | классификатор | 19,0% | 28,6% | 1,0 | 0,8 | 1,1 ч |
| Подтопление | предупреждения отключены: 1 эпизод в периоде настройки | — | — | — | — | — |

Всего около 13 предупреждений в сутки на 78 объектов, примерно 6,5 за 12-часовую смену. Ориентир брифа 0,7 / 0,5 на реальном журнале не достигнут. Для охраны на мае сравнивались классификатор, модель числа эпизодов и их смеси (доля модели числа эпизодов 0,25 / 0,5 / 0,75) с одним правилом: наибольшая полнота при точности не ниже 0,7. Смесь 0,75 на мае дала 0,702 при полноте 0,444 — больше, чем модель числа эпизодов (0,716 / 0,321) и классификатор (0,792 / 0,097), поэтому выбрана она. На июне точность смеси 0,578 при полноте 0,402: запас по точности на мае был минимальным, на отложенном месяце она ниже 0,7. Модель числа эпизодов на той же проверке давала 0,650 / 0,318 — если важнее точность, это вторая рабочая точка. Для пожара и неисправностей точность 0,7 на мае недостижима ни при каком пороге, порог выбран по F1. Строгая полнота «один к одному» по отдельным эпизодам: охрана 12,4%, пожар 15,3%, неисправности 31,6%. Прежний подсчёт, где предупреждение засчитывалось за любой последующий эпизод, давал охране 77,7% и пожару 49,4% точности — он завышал результат за счёт продолжения уже идущих суток.

Прежняя версия (`op-7f225ca12c58`) допускала повтор предупреждения по объекту через час и на том же июне давала охрану 76,3% / 63,2% при 41 предупреждении в сутки и пожар 61,8% / 42,0% при 9 в сутки: повторы по одному шумному объекту засчитывались как отдельные попадания. Воспроизведение обеих: `scripts/release_daily_rule.py`, отчёт — `artifacts/daily_rule_evaluation.json`. Исходная проверка классификаторов на 3-часовой сетке — в [MODEL_CARD.md](docs/MODEL_CARD.md).

### Полигон

Реальные пожары, проникновения и подтверждённые отказы в данных не размечены, поэтому цифры выше — качество прогноза записей журнала, а не распознавания аварий. Распознавание проверяется на полигоне.

Полигон — это реальный журнал 2026 года, поверх которого записаны инциденты с известной правдой и реестры, которых нет в выгрузке: наряды-допуски, огневые работы, паспорта насосов и вентиляторов. Модели учились на январе–апреле 8 миров, пороги выбраны на мае, проверка — июнь 10 других миров. Подробно, с допущениями и ограничениями: [docs/POLYGON.md](docs/POLYGON.md).

| Июнь, 10 миров | Результат | В сутки на весь парк |
|---|---|---|
| Пожарная тревога: возгорание или сварка | 13 из 17 возгораний подняты; 1 ложный подъём — тревога от сварки по наряду, остальные ~420 тревог от сварки узнаны по наряду | ~20 тревог → 0,06 подъёма, ~1,4 «огневые работы» |
| Охранная тревога: проникновение или работа | 61 из 64 проникновений, точность 65% | ~45 тревог → ~40 по наряду, ~4,8 звонка, 0,29 выезда |
| Прогноз возгорания | 8 из 17 заранее, за 2,6 ч; где есть датчик температуры — 8 из 9 | 0,13 предупреждения |
| Отказ насоса | 14 из 19, за 11,4 ч, точность 54% | 0,09 предупреждения |
| Отказ вентилятора | 10 из 13, за 11,6 ч, точность 2,9% — шумно | 1,13 предупреждения |
| Газ при отказе вентиляции | 10 из 12, за 5,4 ч, точность 77% | 0,04 предупреждения |
| Каскад сбоев | 77 из 78 распознаны как сбой оборудования | одно сообщение вместо десятков |

На хитрых мирах (больше дневных проникновений, работ и сварки без наряда, возгораний во время сварки и тлеющих) с теми же моделями и порогами результаты меняются в пределах разброса: проникновения 64 из 71, возгорания 20 из 21; насосы — 7 из 18, прогноз износа на малых выборках неустойчив. Прогон воспроизводим: два полных прогона дают побайтно одинаковый отчёт, версии библиотек и хеши входов записаны в отчёт. Это проверка того, что сервис отрабатывает сценарии, а не точность на реальных авариях: формы сигналов и частоты — допущения команды.

Реальные метрики выше и полигон не смешиваются. Подробно: [MODEL_CARD.md](docs/MODEL_CARD.md), исследования: [docs/research/RESEARCH_LOG.md](docs/research/RESEARCH_LOG.md), машинные отчёты: `artifacts/evaluation_report.json`.

Производительность локального стенда: пересчёт 312 прогнозов — около 20 с; 20 одновременных сеансов / 100 запросов — 0 ошибок, p95 374 мс (`artifacts/performance_report.json`).

## Импорт и API

Импорт принимает журнал СМВУ в том виде, в каком он выдан командам (`ид_события, ид_канала_данных, дата, время, значение_датчика, тревожное`), схему приложения 1 ТЗ (`ИД канала данных, Текущее значение, Дата записи`) и формат `channel_id, ts, value, alarm`. Разделитель определяется автоматически, кодировка UTF-8 или Windows-1251, до 300 МБ и 2 млн строк. Если флага тревоги нет, он восстанавливается по истории канала. Нераспознанные строки (до 5%), каналы вне справочника и записи позже момента прогноза пропускаются и показываются в результате. Время без зоны — МСК.

Интерактивный контракт: `/docs`. Основные маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/overview?as_of=...` | Очередь прогнозов: архив и последний расчёт по новым данным |
| GET | `/api/forecast/{object_id}/{kind}` | Факторы, история, исходные записи |
| POST | `/api/decisions` | Решение диспетчера и основание |
| POST | `/api/imports?format=csv` | Расчёт по файлу аналитика (ответ 202), результат попадает в очередь диспетчера |
| GET | `/api/imports/{id}` | Состояние и результат расчёта |
| POST | `/api/stream/events?format=json&as_of=...` | Пакет потока СМВУ: квитанция и расчёт |
| GET | `/api/equipment` | Состояние оборудования |
| GET/POST | `/api/tasks`, `/api/work-orders` | Задачи и заявки |
| GET/PUT | `/api/labels` | Верификация меток |
| GET/POST | `/api/thresholds/preview`, `/api/thresholds/proposals` | Пороги: эффект, предложение, утверждение |
| GET | `/api/summary`, `/api/reports/summary.pdf`, `.xlsx` | Сводка и отчёты |
| GET/POST/PATCH | `/api/users` | Пользователи и роли |
| GET | `/api/export/forecasts.csv`, `.xml`; `/api/topology.geojson` | Выгрузки |
| GET | `/api/polygon`, `/api/polygon/feed` | Результаты полигона и лента июня |
| GET | `/api/polygon/dataset.zip`, `/api/polygon/journal.csv?day=...` | Синтетический датасет и журнал полигона за сутки |
| GET | `/api/ready` | Готовность БД и моделей |

Координат объектов в данных нет: схема строится по справочной иерархии, GeoJSON содержит `geometry: null`.

## Архитектура

- `src/moscollector/prepare.py`, `features.py` — нормализация архива, эпизоды, причинные признаки.
- `train.py`, `count_release.py`, `alert_policy.py` — CatBoost, калибровка, пороги, выпуск модели.
- `daily_rule.py` — правило «одно предупреждение на объект и тип в сутки» и метрики по неспокойным суткам; `scripts/release_daily_rule.py` — выбор порогов и выпуск пакета.
- `api.py`, `service.py`, `roles.py` — FastAPI, роли и права, аудит.
- `importing.py`, `batch.py`, `streaming.py` — импорт, отдельный процесс расчёта, приём потока.
- `workorders.py`, `reports.py` — заявки (эмуляция внешней системы), отчёты PDF/XLSX.
- `polygon.py`, `polygon_scenarios.py`, `polygon_units.py`, `polygon_view.py` — полигон: генератор инцидентов и реестров, распознавание сценариев, выдача результатов; `scripts/polygon_run.py` — прогон и отчёт.
- `web/` — React + TypeScript.
- `compose.yaml`, `deploy/` — PostgreSQL, TLS, резервное копирование.
- `src/moscollector/experiments/`, `scripts/research/`, `docs/research/` — исследовательский код и отчёты; сервисом не используются.

Собственная БД хранит пользователей, решения, заявки, метки, пороги и аудит (SQLite локально, PostgreSQL 16 в Docker). Источники заказчика только читаются.
