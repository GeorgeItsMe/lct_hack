# Разбор задачи №8 Москоллектор

Дата изучения: 21 сентября 2026 года.

Нужно разработать сервис поддержки диспетчера, который заранее оценивает риск отказов оборудования и инцидентов в инженерных коллекторах, объясняет предупреждения, рекомендует обслуживание и сохраняет решения человека. Основной риск проекта — доказать именно прогнозирование будущего события при отсутствии подтверждённой разметки реальных инцидентов.

**Что должен делать продукт**

Основной пользователь — диспетчер. Дополнительные пользователи — технический персонал и руководитель эксплуатационного подразделения.

Рабочий сценарий: данные мониторинга → прогноз → уведомление → карточка с обоснованием → проверка диспетчером → решение и причина → запись в журнал. История решений становится материалом для последующего улучшения моделей.

Направления из ТЗ:

- Прогноз отказов датчиков и инженерных систем.
- Раннее выявление риска пожара и подтопления.
- Аналитическая поддержка проверки несанкционированного доступа.
- Рекомендации по техническому обслуживанию на основе состояния оборудования.

Система не принимает окончательное решение, не управляет оборудованием и не выполняет ремонт. Доступ к внутренним системам заказчика — только чтение. Сохранение решений диспетчера происходит в собственном сервисе.

**Выводы для модели и проверки качества**

Следующие пункты — аналитические рекомендации по итогам изучения, а не дополнительные требования организаторов.

1. Формально определить предсказываемое событие до обучения. Например, новый эпизод неисправности, подтверждённый заданной длительностью. Это прокси-метка технического состояния; её нельзя автоматически назвать подтверждённым физическим отказом.
2. Для прогноза в момент `t` использовать только информацию, доступную к `t`. Таргет — начало нового события в будущем окне `(t, t+H]`. Уже активный отказ относится к текущему состоянию. Будущая длительность эпизода допустима для формирования метки, но не как входной признак в момент прогноза.
3. Флаг тревоги, дым или затопление сами по себе не подтверждают реальный пожар или подтопление. Метрики по таким меткам измеряют предсказание зарегистрированных событий. Симуляция подходит для демонстрации интерфейса, но не доказывает качество на реальных инцидентах.
4. Проверять качество по времени: ранний период для обучения, следующий для настройки, поздний для финального теста. Удалять обучающие примеры, чьи будущие окна меток заходят в следующий период. Настройку порогов и калибровку завершать до финального теста.
5. Пример за один день августа, если описание брифа подтвердится, недостаточен для полноценной независимой проверки 24-часового горизонта: нужны предыстория и наблюдаемое будущее. Использовать его для проверки импорта, интерфейса или отдельно обоснованного короткого горизонта.
6. Forward-fill отражает последнее известное состояние. Сохранять возраст наблюдения и признак неизвестного состояния; не заполнять из будущего и не переносить состояние без ограничений через разрывы выгрузки. Стабильное значение при событийной записи само по себе не означает зависший датчик.
7. Сохранять исходные значения, отделять измерения от кодов состояния. Проверять sentinel-коды с учётом типа датчика. Удаление таких значений без сохранения признака ошибки может убрать полезный сигнал отказа.
8. Не удалять разные события только из-за одинакового ID или секунды. Отделять точные дубликаты от конфликтующих записей; фиксировать устойчивое правило обработки неоднозначности.
9. Группировать каскады по доступным признакам общей причины, объекту и временному окну. Близость во времени сама по себе не доказывает один инцидент. Показывать результаты на уровне каналов и сгруппированных эпизодов.
10. Помимо Precision/Recall показывать число эпизодов, число пропусков, ложные предупреждения на объект за сутки и фактическое время упреждения. Не считать один эпизод многими успешными прогнозами из-за повторных уведомлений.
11. Начать с простых правил и статистической базовой модели. Сложную модель принимать только при улучшении на отложенном периоде. Число от 0 до 1 из детектора аномалий не становится вероятностью без обоснованного преобразования и проверки калибровки.
12. Счётчики тревог из брифа не равны количеству независимых инцидентов. Выбирать дополнительный сценарий после оценки числа эпизодов и наличия предвестников.

**Предлагаемый старт разработки**

Рабочая гипотеза: первым довести до проверяемого результата прогноз неисправностей оборудования, затем добавить один сценарий инцидента, выбранный по данным. Возможность ограничить охват одним или двумя направлениями опирается на бриф и требует сохранённого подтверждения организаторов.

Последовательность работ:

1. Скачать справочники, пример и архив 2026 года. Проверить схему, даты, часовой пояс, связи, состояния, дубликаты, пропуски и число независимых эпизодов. При необходимости расширить историю другими годами.
2. Зафиксировать определение события, правила очистки, горизонт 24 ч, временные разбиения и сопоставление предупреждений с событиями. Отдельно учесть цензурирование у границ файлов и разрывы наблюдения.
3. Построить воспроизводимый базовый прогноз и отчёт по отложенному периоду. По результату решить, какие сценарии действительно поддаются раннему предсказанию.
4. Собрать полный путь диспетчера: дашборд → схематичная карта → карточка прогноза → объяснение и рекомендация → решение с причиной → журнал.
5. Подключить импорт и воспроизведение исторического потока, REST API, рабочую БД, роли, аудит действий и настройки порогов. Демонстрационные координаты и внешние адаптеры явно обозначить.
6. Подготовить запуск на Linux, проверить скорость и 20 одновременных пользователей, написать документацию и подготовить презентацию по исходному шаблону.

Разделение компонентов: импорт и контроль качества → хранение событий и справочников → признаки и модели → прогнозы и рекомендации → API и интерфейс. Отдельные компоненты: оценка качества, история решений, журнал действий, адаптеры внешних систем.

В финальной экспертизе прямо проверяются соответствие прогнозов реальным данным, достоверность диаграмм, обоснованность рекомендаций, настраиваемые параметры и удобство. Воспроизводимый показ «что было известно в момент прогноза → что предсказано → что случилось позже» должен быть центральной частью демонстрации.
