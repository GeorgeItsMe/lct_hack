# Роли и рабочие места

Сервис разделяет пользователей по ролям. У каждой роли свой набор разделов и своя стартовая страница: раздел 16 ТЗ требует, чтобы элемент интерфейса был на экране, только если он нужен для задач пользователя. Права проверяются на сервере для каждого запроса; интерфейс лишь скрывает недоступное. Единый источник матрицы — `src/moscollector/roles.py`.

## Откуда взяты роли

| Роль | Основание в ТЗ | Суть работы |
|---|---|---|
| Диспетчер | Раздел 3 (диспетчеры ОДС и эксплуатационных подразделений), разделы 10 и 12 | Получает предупреждение, проверяет ситуацию, фиксирует решение с причиной |
| Технический персонал | Раздел 3; разделы 4, 6, 8 (прогноз отказов, рекомендации по ТО, черновики заявок) | Состояние оборудования, работы по решениям диспетчера, черновики заявок |
| Аналитик | Раздел 12: участник обоих сценариев, «ответственный за верификацию данных»; итог сценария — «анализ и дообучение модели» | Качество данных и решений, загрузка данных, проверка модели, предложение порогов |
| Руководитель подразделения | Раздел 3; раздел 8 (аналитические отчёты для руководства, статистика по типам, сезонность) | Сводка по узлам и типам, отработка предупреждений, отчёты, утверждение порогов |
| Администратор | Раздел 11 (RBAC, LDAP/AD, журналирование всех действий). Пользователем в ТЗ не назван — служебная роль | Учётные записи, роли, зоны ответственности, журнал аудита |

Аналитик в разделе 3 не перечислен, но назван участником сценариев раздела 12. Бриф (ответ организаторов, п. 3.2) оставляет состав ролей на усмотрение команды.

Проверку конкретного сигнала (датчики, камеры, плановые работы) выполняет диспетчер — так в шаге 4 сценария ТЗ и в реальной смене ОДС, где один из сотрудников контролирует системы мониторинга ([mos.ru](https://www.mos.ru/news/item/23399073/)). «Верификация данных» аналитика относится к данным для обучения и оценки модели.

## Сквозной сценарий

1. **Диспетчер** видит новое предупреждение (всплывающее уведомление, уровень риска), открывает карточку: факторы, рекомендации с основанием из журнала датчиков, блок проверки ситуации, календарный контекст. Выбирает действие из сценариев ТЗ: «Выезд бригады», «Направить бригаду на проверку», «Мониторинг ситуации», «Ложное срабатывание», «Запланировать ТО».
2. **Технический персонал** получает задачу, формирует черновик заявки (объект, прогноз, решение, факторы, рекомендации), правит его и передаёт в систему учёта заявок. Статус приходит обратно только на чтение.
3. **Аналитик** видит пару «прогноз → решение → итог работ → факт по журналу» с предложенной меткой, принимает или исключает её, фиксирует набор для дообучения. Для порога видит эффект на периоде настройки и отправляет предложение с обоснованием.
4. **Руководитель** утверждает или отклоняет порог, смотрит сводку по узлам, динамику, сезонность, отработку и итоговое качество прогноза, выгружает отчёт. Подробная проверка модели и качество данных — рабочие инструменты аналитика.
5. **Администратор** видит все шаги в журнале аудита.

Проверка на запущенном стенде: `python scripts/verify_roles.py --url http://127.0.0.1:8000`.

## Допущения и ограничения

- **Система учёта заявок эмулируется.** По разделу 6 ТЗ заявки ведёт внешняя система, сервис получает статусы. Организаторы разрешили mock-интеграцию при условии правдоподобности. Эмулятор меняет статус со временем (`CONTOUR_WORKORDER_STEP_SECONDS`, по умолчанию 20 с на шаг), а итог берёт из архива: начался ли эпизод в течение 24 часов после прогноза; при неисправных каналах объекта без эпизода — «сбой датчика». Случайных чисел нет.
- **Дообучение — техническая возможность.** Аналитик фиксирует набор проверенных меток (CSV в `data/runtime/retraining/`). Обучение новых весов требует полного подготовленного датасета, которого нет в демо-пакете; команда указана в записи набора. Новые веса активируются только после проверки на отложенном периоде.
- **Эффект порога** считается на периоде настройки порогов (16–31 мая 2026) той же функцией, что и при обучении (`alert_policy.alert_metrics`), и точно воспроизводит сохранённые метрики модели. Июньский тест для подбора порога не используется.
- **Зона ответственности.** У пользователя есть поле «весь район» или «узел». В справочнике объектов один район, поэтому в демо у всех «весь район»; зона «узел» ограничивает прогнозы, сводку и оборудование объектами узла.
- **LDAP/AD.** Вход через LDAPS поддерживается, роль сотрудника назначает администратор. Автоматическое сопоставление групп каталога с ролями не реализовано.
- **Уровни риска** задаются относительно порога типа: критический — вероятность не ниже удвоенного порога (но не выше 95%), высокий — выше порога, повышенный — от половины порога. Поэтому уровни остаются осмысленными после смены порога.
