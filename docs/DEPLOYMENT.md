# Развёртывание и восстановление

## Локальный и промышленный режимы

Локально используются SQLite и loopback HTTP. Docker запускает тот же код с PostgreSQL 16. Плановый минимум для стенда: 4 CPU, 8 ГБ RAM, около 3 ГБ для образа и runtime-пакета, отдельно место для исходных данных и копий. Это стартовая конфигурация, ресурсную ёмкость на целевом сервере нужно измерить. GPU не требуется.

`CONTOUR_DEMO=true` создаёт три демонстрационные учётные записи. Для production задайте `CONTOUR_DEMO=false`, новый том PostgreSQL и `CONTOUR_ADMIN_PASSWORD` длиной не менее 12 символов. Существующая БД с известным демо-паролем блокирует запуск production. Пароли БД в строке подключения должны быть URL-кодированы; для простой настройки используйте случайное шестнадцатеричное значение. Не храните `.env` в репозитории.

Проверьте `/api/ready`, войдите, откройте прогноз и сохраните контрольное решение. По умолчанию опубликован только `127.0.0.1:8000` или выбранный `CONTOUR_PORT`. Для удалённого доступа используйте согласованный reverse proxy или защищённый туннель. Публичное развёртывание в текущей работе не выполнялось.

## TLS и LDAP

Для профиля `tls` положите действующий сертификат и ключ в `deploy/certs/fullchain.pem` и `privkey.pem`. Выполните `docker compose --profile tls up -d`. Caddy слушает loopback 8443 и допускает TLS 1.2–1.3. Браузер должен доверять сертификату; проверки сертификатов не отключаются. Production-cookie использует Secure, HttpOnly, SameSite=Strict.

Поддержан необязательный LDAPS bind для предварительно заведённых пользователей. Настройки: `CONTOUR_LDAP_URL=ldaps://directory.example:636`, `CONTOUR_LDAP_BIND_TEMPLATE={username}@example`, при необходимости `CONTOUR_LDAP_CA_FILE=/certs/ldap-ca.pem`. Сервис проверяет сертификат, запрещает перенаправление учётных данных на LDAP referrals, использует соединение только для чтения. Локальный `admin` остаётся аварийной учётной записью. Роли назначаются в собственной БД, автоматического расширения прав по группам каталога нет.

Создание пользователя:

```bash
docker compose exec api python -m moscollector.users employee --name 'Диспетчер' --role dispatcher --ldap
```

Без `--ldap` команда запрашивает локальный пароль интерактивно. Реальный сервер LDAP/AD не был предоставлен, поэтому интеграционное испытание каталога остаётся обязательным шагом пилота. Основа клиента: [официальная документация ldap3 о TLS](https://ldap3.readthedocs.io/en/latest/ssltls.html) и [соединениях](https://ldap3.readthedocs.io/en/latest/connection.html).

## Резервные копии

Контейнер `backup` каждые 6 часов создаёт пару `pg_dump -Fc` + архив runtime-тома, сначала пишет `.partial`, затем переименовывает и сохраняет общий SHA-256-манифест. Копии находятся в `backups/`. БД копируется первой, завершённые снимки неизменяемы и не удаляются, поэтому копия тома включает файлы, на которые ссылаются решения в дампе. Промежуточные каталоги вычисления и worker.log исключаются. Незавершённые задания после восстановления требуют повторного расчёта. Удаление старых копий не выполняется автоматически. Нужен контроль свободного места и перенос копий во второй согласованный домен хранения. Артефакты модели и неизменяемый runtime-пакет сохраняйте отдельно с манифестом SHA-256.

Операционные решения, пользователи, сеансы, настройки, аудит, накопленные события `stream_events` и квитанции `stream_batches` попадают в копию PostgreSQL. Снимки расчётов, их признаки и результаты из тома `runtime_data` входят в парный runtime-архив. Они не входят в сам pg_dump. Последний момент потока можно пересчитать из восстановленной БД; это не восстанавливает автоматически старые ID снимков. Во время остановки процесса незавершённый пакет получает статус ошибки и может быть подан повторно.

В дополнительной проверке новая БД `contour_restore_stream_20260921` восстановила 1 389 событий, две квитанции и три диспетчерских решения. Runtime восстановлен в новый том `contour_restore_runtime_20260921`. Отдельный контейнер прочитал восстановленные решения и заново получил восемь SHAP-факторов для связанных снимков. Рабочие БД и том не перезаписывались. Это проверка небольшого локального стенда.

## Восстановление без перезаписи рабочей БД

1. Проверить SHA-256 файла копии и наличие runtime-пакета нужной версии.
2. Запустить PostgreSQL и восстановить в **новую** базу: `./deploy/restore.sh backups/contour-....dump contour_restore_check`.
3. Восстановить парный архив в **новый** том: `./deploy/restore_runtime.sh backups/contour-....runtime.tar.gz contour_restore_runtime_check`. Команда отказывается перезаписывать существующий том.
4. Подключить отдельный экземпляр API к новой БД и новому runtime-тому, сохранив read-only mounts артефактов и processed-данных. Проверить количество решений, аудит, вход, `/api/ready` и объяснения снимков, на которые ссылаются решения. Для Compose смена тома задаётся отдельным override с `volumes.runtime_data.external: true` и `name` нового тома.
5. После проверки согласованно переключить `DATABASE_URL` и runtime-том рабочего API. Исходные базу и том сохранить до окончания проверки.

Требование ТЗ — восстановление до 4 часов. Время локальной репетиции фиксируется отдельно в отчёте испытаний; оно не включает восстановление инфраструктуры заказчика и сетевые задержки. Регулярно проводите репетицию на фактическом объёме данных.

## Эксплуатационные ограничения прототипа

Один API worker использует внутреннюю очередь до четырёх пакетов с одним процессом расчёта; каждый расчёт ограничен 300 секундами. Для нескольких реплик очередь нужно вынести в отдельный сервис. Нельзя запускать несколько API workers над одним каталогом импортов. Само API читает замороженные прогнозы, а пакетный worker вычисляет новые признаки и прогнозы.

Шлюз СМВУ отправляет обезличенные пакеты через `POST /api/stream/events` с сеансом пользователя, которому разрешён импорт. Приём выдаёт долговечную квитанцию независимо от доступности очереди расчёта. Повторы безопасны, момент потока монотонен. Клиент должен проверять `job`, `forecast_error`, затем статус задания; ответ 202 сам по себе не означает готовый прогноз. До подключения реального шлюза `external_system_connected` остаётся false. Накопление не ограничено общим числом строк, но создание снимка материализует историю текущего года в памяти; для промышленного объёма нужны нагрузочное испытание, секционирование и инкрементальный encoder. Исходные события автоматически не удаляются.

Сбой пакета не изменяет исходный архив. Одновременные изменения одной диспетчерской записи используют модель «последняя запись побеждает», предыдущие значения сохраняются в аудите. На промышленном пилоте рекомендуется контроль версии записи. Аудит защищён ролью приложения, но не является криптографически неизменяемым журналом.

Кластер пользователя сейчас не нужен: CPU-обучение и инференс укладываются в локальные ресурсы. Если появится отдельный эксперимент на GPU, запускать только через Slurm, с одной картой в задании; не выполнять Python на login-узле. Старые скрипты `train_native.sbatch` относятся к другому проекту и в это решение не перенесены.
